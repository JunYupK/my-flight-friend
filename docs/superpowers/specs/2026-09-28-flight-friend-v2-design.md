# Flight Friend V2 — Design Spec

- 작성일: 2026-09-28
- 상태: 브레인스토밍 합의안 (구현 계획 작성 전)
- 범위: 제품 정의 · 데이터/검색 모델 · UX/IA · 아키텍처 · 기존 자산 처리 · 마일스톤 · 리스크

---

## 1. 배경 — V1에서 무엇이 틀렸나

V1은 "일본 여러 도시 × 향후 12개월"을 3시간 cron으로 광역 수집해 목적지별 최저가를 보여주는
**가격 추이 관찰 도구**였다. 운영해 보니 두 가지가 실제 사용과 어긋났다.

1. **가격 신뢰성.** 화면 가격과 실제 예약 가능 가격의 괴리가 컸다. 코드 조사 결과 원인은
   "배치라서 늦음"만이 아니라 **관측 모델 자체의 왜곡**이었다.
   - `flight_legs` UPSERT가 `price = LEAST(new, old)` — 가격이 오르면 반영되지 않고 `checked_at`만 갱신.
   - `deals.last_checked_at`은 관측 시각이 아니라 조합 재계산 시각(`combine_roundtrips`의 `now()`).
   - `get_collected_today()` 스킵 + 월 슬라이싱 → 실제 날짜별 갱신은 소스당 하루 1회 이하.
   - 날짜별 최저가 Top-5(`topk_per_date`)만 저장 → 시간대 조건을 걸면 후보 자체가 없음.
   - **실측 (OCI, 2026-09-28):** `flight_legs` 표시가를 같은 항공편의 최신 `raw_legs` 관측가와 비교하면
     191,605개 레그 중 **58%가 낮게 표시**, 평균 **+11.0%**, p90 **+33.7%** 괴리.
2. **제품 관점.** 실제 여행은 "날짜 결정 → 여행지 → 검색 → 며칠 뒤 재검색 → 예약" 순서다.
   "후쿠오카가 요즘 얼마인가"(Destination 중심)가 아니라 "10/21~10/25 미야코지마 항공권"(Trip 중심)이 출발점이다.

V2는 이 두 교훈을 반영한 **Trip 중심 + 정직한 관측 + 사용자 트리거 재확인** 제품으로의 진화다.

## 2. 제품 정의

**한 문장:** 여행 날짜와 원하는 항공편 조건을 한 번 입력하면, Flight Friend가 항공권 검색 서비스를
대신 반복 조회·비교하고, 그 여행의 가격을 계속 지켜본다.

- **사용자:** 본인 1인 (개인 도구). PoC 이후 지인에게 열 여지만 남긴다 — 인증/계정은 만들지 않고,
  조건·목표가 등 모든 설정을 전역이 아닌 **Trip 단위**로 둔다 (추후 `owner` 컬럼 추가로 확장 가능).
- **성공 기준 (마일스톤 2 기준):** Trip을 입력한 뒤 실제 예약 버튼을 누르기 전까지 **Google Flights와
  Naver 항공권을 직접 열 필요가 없다.** (Skyscanner 수집기는 폐기된 RapidAPI v1 기반으로 동작하지 않아 범위에서 제외.)
- **하지 않는 것:** 구매 시점 예측("지금 사세요", 상승 확률), 특정 항공편 하나의 추적, 광역 목적지 탐색,
  다중 사용자/인증, 네이티브 앱.

## 3. 도메인 모델

| 개념 | 정의 |
|---|---|
| **Trip** | 정체성 = 출발공항 · 도착공항 · 출국일 · 귀국일 · 인원 · 좌석등급. 여기에 **선호 조건**, 추적 on/off, 선택 목표가를 가진다. 정체성이 바뀌면 다른 Trip이다. |
| **선호 조건 (preferences)** | 출국/귀국 시간대, 직항 여부, 항공사 포함/제외, 최대 가격, 최대 소요시간 등. **검색 범위를 바꾸지 않는 view-level 필터**다. 변경 즉시 반영되며 재검색이 필요 없다. |
| **검색 실행 (search run)** | 한 Trip에 대한 1회 검색. 트리거는 `schedule`(자동 갱신) 또는 `manual`(사용자 버튼). 둘은 **같은 작업**이다. |
| **스냅샷 (snapshot)** | 검색 실행 안에서 제공자 × 검색 종류(편도 out / 편도 in / 왕복) 하나의 결과. 상태 `ok / empty / blocked / error`와 관측 시각을 가진다. |
| **편도 견적 (leg quote)** | 스냅샷 안의 항공편 1건 = (항공편 식별키, 가격, 예약 링크 …). **불변 기록.** |
| **왕복 참고 견적 (rt quote)** | 왕복 검색 스냅샷의 출국편별 왕복 최저 총액 (항공사별 "왕복이면 얼마" 표시용). |

**Trip과 검색의 관계:** Trip이 곧 검색이다. 조건을 입력하면 Trip이 생성되고 첫 검색이 실행되며,
결과 화면이 곧 Trip 화면이다. "추적"은 저장/전환이 아니라 Trip의 on/off 속성이다.

## 4. 가격 신뢰성 모델

### 4.1 관측 원칙

1. **스냅샷 원칙:** 현재 상태 = 제공자·검색 종류별 **가장 최근 `ok` 스냅샷**. 과거 스냅샷과 병합하지 않는다
   (V1의 `LEAST` 누적 금지).
2. **사라진 항공편은 사라진 것:** 최근 `ok` 스냅샷에 없는 항공편의 그 제공자 가격은 현재가가 아니다.
3. **제공자 실패 시:** 그 제공자는 직전 `ok` 스냅샷을 유지하되 관측 시각을 그대로 드러낸다.
4. **대표 가격 계산은 신선도 기준 시간 W 이내 스냅샷만 사용.** 카드 헤드라인 가격, 대표 후보, 추적 가격이
   여기에 해당한다. W를 넘은 가격은 제공자별 목록에 "오래됨"으로만 흐리게 표시한다. W = 자동 갱신 주기 × 2.
5. **실행 상태를 Trip 상단에 노출:** `마지막 확인 14:20 · Google Flights ✓ · Naver ✕ (차단 의심) [다시 시도]`.
   실패는 결과 0건(차단 가능성)과 오류/타임아웃을 구분한다.

### 4.2 가격 표현

- 가격 개념은 **"확인가 · N분 전" 하나**로 통일한다. "라이브 가격"과 "관측 가격"을 별개 종류로 두지 않는다.
  시간이 지날수록 시각적 강조를 낮춘다.
- 관측 시각은 목록 머리에 한 번 표시하고(`출국편 · 42개 · 2시간 전 확인`), 카드에는 **예외(일부 제공자 가격이
  오래됨)일 때만** 표시한다.

## 5. 검색 실행

### 5.1 트리거

- **페이지 방문 시 외부 조회하지 않는다.** 저장된 관측을 보여준다.
- **수동:** Trip 화면의 `지금 확인` 버튼. 최근 5분 내 확인이 있으면 쿨다운(버튼 비활성, "방금 확인됨").
- **자동:** 추적 on인 Trip만, 출발까지 남은 기간에 따라 단계적 주기. 추적 off 또는 출발일 경과 시 중단.

| 출발까지 | 자동 갱신 주기 (잠정) |
|---|---|
| > 60일 | 6시간 |
| 15–60일 | 2시간 |
| ≤ 14일 | 1시간 |

> 숫자는 잠정값. 구조(단계적 주기, W = 주기 × 2)만 확정. OCI 반복 측정(차단 시작 간격) 결과로 확정한다 (§12).

### 5.2 1회 검색 구성 (마일스톤 1)

| 페이지 | 용도 |
|---|---|
| Google Flights 편도 ICN→DEST (출국일) | 출국편 목록 |
| Google Flights 편도 DEST→ICN (귀국일) | 귀국편 목록 |
| Google Flights 왕복 (출국일, 귀국일) | 항공사별 왕복 참고가 |

- 3페이지 동시 실행. 실측 페이지당 8–10초, 브라우저 기동 0.8–2.8초 → **1회 약 10–13초 예상**.
- 마일스톤 2에서 Naver 편도 out/in 2페이지 추가.
- 검색 URL은 **템플릿 없이 코드로 생성**한다 (protobuf `tfs`; 실측으로 DB 템플릿과 구조 동일 + 실제 결과 수신 확인).
  V1의 공항별 `tfs` 수동 입력 단계는 제거한다.

### 5.3 대기 경험

- 기존 결과를 유지한 채 상단에 제공자별 진행 상태를 표시하고, 완료(또는 타임아웃) 시 **결과를 한 번에 교체**한다.
- 클라이언트는 실행 상태를 2–3초 간격 **폴링**. SSE/WebSocket·제공자별 점진 병합은 도입하지 않는다
  (대기가 1분 이상으로 측정되면 재검토).
- 첫 검색(Trip 생성 직후)만 빈 화면 — 제공자별 진행 상태와 예상 소요시간을 표시.
- 자동 갱신은 조용히 수행하고 "마지막 확인" 시각만 바뀐다.

## 6. 결과 모델

### 6.1 항공편 식별과 제공자 병합

- **식별키:** `날짜 | 출발공항 | 도착공항 | 출발시각 | 도착시각 | 경유수 | 항공사 IATA`.
  편명은 있으면 부가 속성(예약 링크, 검증용)으로 저장한다.
- **항공사 정규화 필수.** 실측에서 같은 항공사의 표기 차이(`스쿳항공/스쿠트항공`, `Trinity Airways/티웨이항공`,
  `Aero K Airlines/에어로케이` 등)와 같은 시각의 다른 항공사(`대한항공/아시아나항공` 1,382건, 공동운항 추정)가 모두 확인됐다.
  → 항공사를 키에서 빼면 잘못된 병합이 발생한다. 정규화 매핑(한글/영문/리브랜딩 → IATA)을 확장한다.
- **실패 방향 원칙:** 키는 엄격하게. 판별 실패는 "같은 항공편이 두 카드로 보임(중복)"이어야 하며,
  "다른 항공편이 하나로 합쳐짐(틀린 가격)"이어서는 안 된다.
- **제공자 내부 중복 제거:** 같은 GF 페이지 안에 동일 편명 카드가 중복 추출된다(실측). 어댑터가 식별키로 dedupe.
- 병합은 **편도 단위**. 조합 가격 = 출국편 최저 확인가 + 귀국편 최저 확인가 (편도마다 다른 제공자 가능).

### 6.2 선호 조건 적용

- 후보 풀 = 선호 조건을 만족하는 편도들. 필터가 기본이다.
- **조건 밖 힌트 1줄:** 조건을 **정확히 하나만** 벗어났고, 조건 내 최저보다 의미 있게 싼 항공편이 있으면
  `조건 밖 · 출국 07:30 (설정보다 30분 이름) · 조건 내 최저보다 52,000원 저렴 [보기]`를 표시한다.
  임계값(예: 10% 또는 3만 원)은 구현 시 정한다.

### 6.3 대표 후보

- 조합의 두 축: **가격**, **현지 체류시간** (= 귀국편 출발시각 − 출국편 도착시각).
- 파레토 프론티어(더 싼 어떤 후보보다도 체류시간이 긴 후보)만 남긴다. 보통 2–4개, 4개 초과 시 가격 간격이
  고르게 3–4개로 샘플링.
- 표시는 최저가 대비 트레이드오프: `+32,000원 → 현지 +5시간`. 가중치·"균형" 점수는 쓰지 않는다.
- V1 `select_diverse_deals`(시간대 버킷)는 폐기.

### 6.4 왕복 참고가

- 편도 모델을 유지한다. 왕복 검색 결과로 **항공사별 왕복 최저 총액**을 구해 출국편 카드·조합 바에
  `이 항공사 왕복으로 사면 총 360,600원부터 (편도 합보다 15,431원 저렴)`처럼 참고 표시한다.
- 추적 가격·대표 후보에는 반영하지 않는다 (한계로 명시, §12).
- 실측 (ICN⇄FUK 10/21–10/25): 최저가 수준 차이 1%, LCC 약 −4%(진에어 −10%), 아시아나 −12%, 대한항공 −24%,
  에어서울은 왕복이 +2% 더 비쌈.

## 7. 추적 요약과 알림

### 7.1 추적 값

- 추적 값 = **선호 조건 내 최저 조합 가격** (출국편 조건 내 최저 + 귀국편 조건 내 최저).
  특정 항공편이 아니라 "이 조건으로 지금 살 수 있는 가장 싼 왕복".
- 차트·통계는 **일별 최저값** 기준 (수동 버튼 연타가 통계를 왜곡하지 않도록). "현재"만 최신 실행 값이며,
  §4.1-4의 W 규칙을 적용한다 (W를 넘은 스냅샷은 현재 추적 값 계산에서 제외).
- 통계: 현재 / 추적 시작(첫날) / 추적 이후 최저(날짜 표시) / 추적 중앙값. 변화율은 기준을 명시
  (`추적 시작(9/28) 대비 −12%`).
- **조건 변경 시 이력 전체를 현재 조건으로 재계산** (스냅샷이 전부 남아 있으므로 가능).
- 차트에서 출국편 최저 / 귀국편 최저 선을 토글로 분리해 볼 수 있다.
- 일부 제공자만 성공한 날은 차트 점을 속 빈 점으로 표시.
- 추적 3일 미만이면 비교 통계 대신 `추적 2일째 · 비교 이력 수집 중`.
- "역사적 최저가"라는 표현은 쓰지 않는다 — 항상 "추적 시작 이후".

### 7.2 알림

- **기본:** 추적 값이 "추적 이후 최저"를 의미 있는 폭(예: 3% 또는 1만 원)으로 갱신하면 알림.
  추적 3일 미만에는 보내지 않는다.
- **선택:** Trip별 목표가를 입력한 경우 목표가 이하 진입 시 알림.
- **운영:** 제공자 연속 실패 시 운영 알림.
- 중복 방지: 새 최저 1건당 1회, 같은 폭으로 추가 하락할 때만 재알림. 알림 단위는 Trip.
- 내용: 최저 조합 가격, 현지 체류시간, Trip 링크, 예약 링크.
- 채널: 기존 `notifier.py` (Telegram → Discord fallback) 재사용.

## 8. UX / 정보구조

### 8.1 라우트

| 경로 | 역할 |
|---|---|
| `/` | Trip 목록(홈). 추적 중 Trip을 출발일 순으로: `미야코지마 10/21→10/25 D-23 · 231,000원 · 2시간 전 · 추적 시작 대비 −12%`. 추적 off·출발 경과 Trip은 접힘. Trip이 없으면 곧바로 새 Trip 생성 폼. |
| `/trips/new` | 필수: 목적지·날짜(인원 기본 1). 선호 조건은 선택. 생성 = Trip 생성 + 첫 검색 → Trip 화면으로 이동. |
| `/trips/:id` | Trip 화면 (아래) |
| `/admin` | 검색 실행 이력, 제공자별 성공률·차단 추세, 시스템 상태. 메인 내비게이션에서 분리. |

### 8.2 Trip 화면 (위→아래)

1. 상태 헤더 — 제목·날짜·D-n, 마지막 확인, 제공자별 상태, `지금 확인`
2. 추적 요약 — 현재 / 추적 시작 / 추적 이후 최저 / 중앙값
3. 대표 후보 (2–4개, 파레토)
4. 조건 밖 힌트 (해당 시에만)
5. 전체 결과 — **출국편 목록 + 귀국편 목록** (데스크톱 2열, 모바일 `출국 | 귀국` 탭) + 필터/정렬 바
6. 가격 추이 차트 (기본 접힘)
7. 하단 고정 **선택한 조합 바** — `263,000원 · 현지 4일 1시간 [출국편 예약 ↗] [귀국편 예약 ↗]` (+ 왕복 참고가)

- **필터 바 = 선호 조건 편집기.** 필터를 바꾸면 Trip에 저장되고 요약도 재계산된다. 별도 설정 화면 없음.
- 대표 후보 클릭 → 두 목록에서 해당 편도가 선택된다 (추천과 전체 결과가 같은 풀).
- 편도는 서로 독립이므로 왕복 조합 목록(최대 수천 줄)을 만들지 않는다. 목록당 20–60개 규모
  (실측 FUK 출국 46 / 귀국 34–40) → **무한 스크롤·가상 리스트·페이지네이션 불필요.**

### 8.3 편도 카드 정보 계층

| 단계 | 내용 |
|---|---|
| 1 (한눈에) | 출발→도착 시각, 최저 확인가 |
| 2 (같은 카드, 작게) | 항공사, 직항 여부·소요시간(경유는 주황 강조), 최저가 제공자 + 나머지 수 (`Naver 외 1곳`) |
| 3 (펼침) | 편명·터미널, 제공자별 가격·관측 시각·예약 링크 |
| 4 (예외만) | 일부 제공자 가격 오래됨 |

- 카드 탭 = 선택, `▾` = 펼침 (모바일에서 두 동작을 분리).
- 조합 바의 예약 버튼은 최저가 제공자 링크. 다른 제공자는 카드를 펼쳐서 선택.

## 9. 아키텍처

### 9.1 구성

```
[browser] ──HTTP──▶ [app: FastAPI + React 정적]  ──SQL──▶ [PostgreSQL]
                        (enqueue / read only)                   ▲
                                                                │ claim (FOR UPDATE SKIP LOCKED)
                                          [search-worker: 상주, crawl4ai + Chromium]
                                            - 작업 큐 소비 (search_runs)
                                            - 자동 갱신 스케줄러 (due Trip enqueue)
                                            - 알림 평가 → notifier
```

- **API 컨테이너는 브라우저를 갖지 않는다** (현재 `Dockerfile`과 동일). 수동 확인 = `search_runs`에 작업 INSERT.
- **search-worker는 상주 컨테이너** (`Dockerfile.collector` 기반). 호스트 crontab, `flock`, `timeout` 래퍼,
  좀비 run 청소, 월 슬라이싱은 제거 대상 — 대신 worker가 `running` 상태 10분 초과 작업을 `error`로 마감한다
  (1회 검색 실측 약 10–13초 대비 충분한 여유).
- 큐는 PostgreSQL 테이블로 충분하다 (1인, Trip 수개 규모). Redis/Kafka는 도입하지 않는다.
- 레이어 규칙(AGENTS.md §2: Router → Service → Repository, Router의 collector import 금지)은 유지한다.

### 9.2 제공자 어댑터 인터페이스

```python
async def search_oneway(crawler, dep: str, arr: str, date: str) -> ProviderResult
async def search_roundtrip(crawler, dep: str, arr: str, out_date: str, ret_date: str) -> ProviderResult
# ProviderResult = {status: ok|empty|blocked|error, quotes: list[LegQuote|RtQuote], error: str|None, seconds: float}
```

- V1 collector에서 **순수 부품만 추출**: GF/Naver 카드 추출 JS, `tfs` protobuf 생성, 예약 URL 생성,
  `_AIRLINE_IATA`(확장), 스크롤 JS. 저장·조합·날짜 루프·전역 설정(`sys.modules` 패치)은 가져오지 않는다.
- 차단 판정은 "카드 0건 + 차단 징후"일 때만 (GF 정상 페이지 소스에도 `captcha` 문자열이 존재 — 실측).

### 9.3 데이터 스키마 (초안)

```
trips(id, origin, destination, out_date, ret_date, adults, cabin,
      prefs JSONB, target_price, tracking BOOL, created_at, archived_at)

search_runs(id, trip_id, trigger 'schedule'|'manual', status 'queued'|'running'|'done'|'error',
            requested_at, started_at, finished_at)

snapshots(id, run_id, trip_id, provider, kind 'oneway'|'roundtrip', direction 'out'|'in'|NULL,
          date, status 'ok'|'empty'|'blocked'|'error', card_count, observed_at, error)

leg_quotes(id, snapshot_id, flight_key, airline_iata, airline_name, flight_numbers TEXT[],
           dep_airport, arr_airport, dep_time, arr_time, duration_min, stops,
           price, booking_url, search_url)

rt_quotes(id, snapshot_id, airline_iata, out_flight_key, total_price)

alerts(id, trip_id, kind 'new_low'|'target'|'ops', price, sent_at)
```

- 전부 append-only (스냅샷·견적은 UPDATE 없음). "현재 상태"는 조회 시 최근 `ok` 스냅샷으로 계산.
- 추적 통계는 조회 시 스냅샷에서 계산 (Trip 수개 × 일 수백 스냅샷 규모에서 사전계산 불필요).
- 마이그레이션은 기존 `init_db()` 멱등 패턴 유지.
